# VS-011 — Architecture Boundaries

## IntentSpec

### Problem

VS-010 proves that the initial graph compiles, but the rules are duplicated inside tests and remain implicit for developers and agents. Future slices could add a project, package or assembly dependency without updating every validator consistently.

### Objective

Create one canonical, versioned architecture policy that drives static project checks, compiled-assembly checks and per-layer agent instructions.

### Boundaries

- No editorial behavior.
- No external architecture-testing package.
- No reflection-based execution of product code.
- Only BookStudio assembly references are governed here; framework references remain the SDK responsibility.

## BehaviorSpec

### Canonical policy

`docs/architecture/architecture-policy.json` defines for every project:

- project name;
- project path;
- layer;
- assembly output path;
- allowed project references;
- allowed BookStudio assembly references;
- package-reference policy;
- required AGENTS file.

### Static validation

- every solution project appears once in policy;
- every policy project exists in solution;
- csproj references equal policy references;
- Domain and Application contain no package references;
- every project has scoped AGENTS instructions;
- the policy version is explicit.

### Compiled validation

After Release build, architecture fitness reads PE metadata and verifies that every referenced assembly whose name starts with `BookStudio.` is explicitly permitted by policy.

### Agent boundaries

- Domain: pure business model and invariants; no I/O, providers or orchestration.
- Application: use cases, ports and contracts; no concrete infrastructure.
- Infrastructure: adapters and persistence; no business decisions.
- MCP: protocol translation only; no domain rules or durable workflow ownership.
- OpenCode: OpenCode transport/session adapter only.
- Autopilot: workflow planning; state changes only through Application use cases.
- Worker: job execution and hosting; no direct domain mutation.
- ControlCenter: presentation/composition; no direct persistence.
- Architecture tests: verify policies; never contain product behavior.

### Errors

- policy/project mismatch;
- duplicate policy project;
- illegal csproj reference;
- illegal compiled assembly reference;
- direct package dependency in protected layers;
- missing scoped AGENTS instructions;
- stale output assembly.

## TDD Dual

### RED-I

Governance tests require the policy, ADR and nine scoped AGENTS files before they exist.

### RED-E

The current .NET architecture executable contains a hard-coded graph and does not read policy or inspect compiled PE metadata.

### GREEN-I

Static governance tests validate the canonical policy and all csproj files.

### GREEN-E

A clean Release build followed by architecture fitness validates both project XML and compiled BookStudio assembly references from the same policy.

## Audit M

- M1: policy covers issue and spec.
- M2: one canonical rule source, no duplicated graph.
- M3: negative checks cover project and compiled assembly boundaries.
- M4: PE metadata is read without executing product code.
- M5: a developer or agent receives actionable layer-local instructions.
