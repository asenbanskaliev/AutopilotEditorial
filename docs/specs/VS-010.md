# VS-010 — Solution Baseline

## IntentSpec

### Problem

The repository has governance and validation contracts but no compilable product foundation. Subsequent slices would otherwise create disconnected projects, inconsistent compiler settings and implicit SDK assumptions.

### Objective

Create a reproducible .NET 10 solution with centralized build policy, explicit project boundaries and a real architecture-fitness executable.

### Boundaries

- No editorial domain behavior is introduced.
- No database, HTTP, MCP or OpenCode implementation is introduced.
- No external runtime package is required in this baseline.
- Projects contain only markers and composition placeholders needed to compile.

## BehaviorSpec

### Required projects

- `BookStudio.Domain`
- `BookStudio.Application`
- `BookStudio.Infrastructure`
- `BookStudio.Mcp`
- `BookStudio.OpenCode`
- `BookStudio.Autopilot`
- `BookStudio.Worker`
- `BookStudio.ControlCenter`
- `BookStudio.Tests.Architecture`

### Allowed references

```text
Domain → none
Application → Domain
Infrastructure → Application + Domain
OpenCode → Application
Autopilot → Application + Domain
Mcp → Application + Infrastructure
Worker → Autopilot + Infrastructure + OpenCode
ControlCenter → Application + Infrastructure
Tests.Architecture → none
```

### Build policy

- SDK pinned by `global.json`.
- Target framework `net10.0`.
- Nullable and implicit usings enabled.
- Deterministic builds.
- Continuous integration build enabled through CI property.
- Warnings treated as errors for repository code.
- Package versions managed centrally when packages are introduced.
- Assembly and root namespaces follow project names.

### Clean-checkout journey

```text
checkout
→ dotnet --version
→ dotnet restore BookStudio.slnx
→ dotnet build BookStudio.slnx -c Release --no-restore
→ dotnet run --project tests/BookStudio.Tests.Architecture -c Release --no-build
→ evidence artifact
```

### Errors

- wrong SDK;
- missing project;
- project not present in solution;
- illegal reference;
- target framework mismatch;
- warning promoted to error;
- architecture test failure.

## TDD Dual

### RED-I

Python structure tests require solution/build files, nine projects and exact references before they exist.

### RED-E

A pull request that touches `.cs`, `.csproj`, `.slnx` or central build files must activate `.NET CI`; before implementation the workflow cannot restore/build/run architecture fitness.

### GREEN-I

Structure tests and architecture executable PASS.

### GREEN-E

An approved .NET-capable CI provider restores, builds and executes architecture fitness on a clean GitHub checkout and uploads normalized evidence. The self-hosted provider remains preferred for intensive workloads, but the lightweight baseline may use the hosted fallback approved in `VS-010-CHANGE-001`.

## Audit M

- M1: project list and reference policy match the issue.
- M2: no business logic or package sprawl.
- M3: tests detect missing and illegal references.
- M4: deterministic CI, no secrets, minimal permissions.
- M5: clean checkout journey is executable without undocumented commands.
